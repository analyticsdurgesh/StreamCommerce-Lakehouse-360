# StreamCommerce Lakehouse 360: What It Does, How It Works, And How To Enhance It

This document explains the project in simple but interview-ready language. It is meant for students, junior data engineers, bootcamp learners, and portfolio builders who want to understand the repo deeply before presenting or extending it.

## 1. What This Project Is Doing

**StreamCommerce Lakehouse 360** is an end-to-end Data Engineering project for a fictional e-commerce company named **StreamCommerce**.

The project builds a modern analytics platform that can ingest real-time events, store raw data, clean and validate it, create analytics-ready datasets, and visualize business KPIs in a dashboard.

In practical terms, this project does the following:

1. Simulates real e-commerce source systems.
2. Sends source events to Kafka topics.
3. Lands raw events into local S3-compatible storage.
4. Builds a Bronze layer for raw, replayable data.
5. Builds a Silver layer for cleaned and validated data.
6. Quarantines invalid or suspicious records.
7. Builds a Gold layer for business metrics.
8. Shows KPIs in a Plotly Dash dashboard.
9. Uses Airflow-style DAGs to orchestrate the workflow.
10. Provides Databricks-ready notebooks for cloud/lakehouse execution.
11. Provides Terraform files for AWS S3 infrastructure.
12. Includes tests so the project behaves like a real engineering repo.

The business idea is:

> StreamCommerce wants reliable analytics for orders, revenue, customers, payments, inventory, products, shipments, and data quality.

Instead of analyzing one static CSV file, this project simulates how modern companies handle messy event data from multiple systems.

## 2. The Business Problem

An e-commerce company usually has data spread across many systems:

- Website and mobile app behavior
- Orders
- Payments
- Product catalog changes
- Inventory updates
- Shipment and delivery events
- Customer reference data
- Marketing campaigns

These systems produce data at different speeds and with different quality levels. Some records are late. Some are duplicated. Some fields are missing. Some values are invalid.

The project solves this problem by creating a lakehouse pipeline that turns messy operational data into trusted business-ready analytics.

## 3. Source Of Data

The primary data source is a custom-built synthetic event simulator:

```text
streaming/producers/event_simulator.py
```

This simulator represents production source systems used by an e-commerce company.

It generates events for:

| Source system | Topic | Example events |
|---|---|---|
| Website/mobile app | `customer_events` | `page_view`, `product_view`, `add_to_cart`, `checkout_started`, `search` |
| Order service | `orders` | `order_created`, `order_confirmed`, `order_cancelled`, `order_returned` |
| Payment gateway | `payments` | `payment_success`, `payment_failed`, `payment_pending`, `refund_success` |
| Inventory service | `inventory_updates` | `stock_added`, `stock_reserved`, `stockout_warning` |
| Product catalog service | `product_catalog_updates` | `product_created`, `price_changed`, `category_changed` |
| Shipment service | `shipment_events` | `shipment_created`, `shipped`, `delayed`, `delivered` |

The project also creates batch reference files:

```text
customers.csv
products.csv
warehouses.csv
sellers.csv
locations.csv
marketing_campaigns.csv
```

Those files are generated by:

```text
scripts/seed_reference_data.py
```

This means the project can run without any paid API or external dataset.

## 4. Why The Data Is Realistic

The simulator intentionally generates imperfect data.

Examples of bad data:

- duplicate events
- late-arriving events
- null customer IDs
- missing product IDs
- invalid product IDs
- negative prices
- invalid payment statuses
- missing timestamps
- schema drift
- malformed JSON records
- out-of-order events

This is important because real-world data pipelines are not only about moving clean data from one place to another. A strong data engineering project should show how the system handles dirty, incomplete, late, and inconsistent data.

## 5. High-Level Architecture

The architecture follows this flow:

```text
Event simulator
  -> Kafka
  -> Landing storage
  -> Bronze layer
  -> Silver layer
  -> Quarantine
  -> Gold layer
  -> Dashboard
```

Local development uses:

- Docker Compose
- Kafka
- Airflow
- PostgreSQL
- MinIO
- Plotly Dash
- Local files under `data/`

Cloud/production-style mode uses:

- AWS S3
- Databricks
- Delta Lake
- Airflow orchestration
- Terraform infrastructure

MinIO is used only as a local S3-compatible replacement. AWS S3 is the intended production target.

## 6. How The Project Works End To End

### Step 1: Generate Source Events

Python producers generate synthetic e-commerce events.

Example:

```bash
python -m streaming.producers.event_simulator \
  --source orders \
  --event-rate 3 \
  --duration 120 \
  --bad-data-percentage 10
```

This sends order events into Kafka.

### Step 2: Kafka Stores Events Temporarily

Kafka topics separate each source stream:

```text
customer_events
orders
payments
inventory_updates
product_catalog_updates
shipment_events
```

Kafka allows the data platform to decouple source systems from downstream processing.

### Step 3: Consumer Writes Events To Landing

The landing consumer reads from Kafka and writes JSONL files to landing storage:

```text
streaming/consumers/s3_landing_consumer.py
```

Local output example:

```text
data/landing/orders/processing_date=2026-05-31/events-1030.jsonl
```

Cloud output example:

```text
s3://streamcommerce-lakehouse/landing/orders/
```

### Step 4: Bronze Layer Preserves Raw Data

Bronze ingestion reads landing files and stores raw records with metadata.

Bronze adds:

```text
raw_json
ingestion_timestamp
source_topic
source_file
batch_id
processing_date
```

Bronze does not aggressively clean data. Its purpose is auditability and replay.

### Step 5: Silver Layer Cleans And Validates

Silver transformation parses raw JSON, normalizes fields, deduplicates events, validates important business fields, and separates valid records from invalid records.

Silver handles:

- timestamp standardization
- duplicate removal
- required field checks
- payment status normalization
- price and quantity validation
- malformed record handling
- data quality flagging

Good records go to:

```text
data/silver/
```

Bad records go to:

```text
data/quarantine/
```

### Step 6: Data Quality Framework Scores The Data

The data quality framework is located here:

```text
databricks/src/quality/checks.py
```

It produces one result per check:

```text
passed
failed_record_count
total_record_count
pass_percentage
severity
reason_code
checked_at
```

This helps users explain not just that the pipeline ran, but whether the data can be trusted.

### Step 7: Gold Layer Builds Business Tables

Gold tables are analytics-ready datasets used by the dashboard.

Gold outputs include:

```text
daily_revenue
product_performance
customer_360
inventory_health
payment_reliability
data_quality_scorecard
```

These tables answer business questions like:

- How much revenue did we make?
- What are the top products?
- Which categories perform best?
- How many payments failed?
- Which products have stockout risk?
- Which customers are repeat buyers?
- What is the data quality pass rate?

### Step 8: Dashboard Visualizes KPIs

The dashboard is located here:

```text
dashboard/app.py
```

It reads Gold tables and shows:

- KPI cards
- revenue trend
- order trend
- product performance
- customer analytics
- inventory risk
- data quality health

The dashboard proves that the lakehouse produces usable business outcomes, not only raw files.

## 7. Why This Project Is Robust

This project is robust because it uses patterns that real data teams use.

### It Uses A Layered Lakehouse Design

The Medallion Architecture separates raw, cleaned, and business-ready data:

- Bronze for raw replayable data
- Silver for cleaned trusted data
- Gold for analytics-ready data

This prevents downstream dashboards from reading raw, unreliable events directly.

### It Preserves Raw Data

Bronze keeps the original raw JSON. If a bug is found later, the pipeline can be replayed from raw data.

This is a strong production design pattern.

### It Handles Bad Data Explicitly

Invalid records are not silently dropped.

They are written to quarantine with:

```text
check_name
reason_code
```

This makes debugging easier and makes data quality explainable.

### It Has A Reusable Data Quality Framework

The DQ checks are not hardcoded only for one file. They are implemented as reusable Python logic that can be applied across tables.

The framework produces measurable outputs:

- pass/fail
- failed count
- total count
- pass percentage
- severity

### It Supports Local And Cloud Modes

The repo can run locally using Docker and local files, but it is also designed for AWS S3 and Databricks.

This makes it useful for:

- student portfolios
- local demos
- interview walkthroughs
- cloud deployment practice

### It Is Config-Driven

Configuration lives in:

```text
configs/local.yaml
configs/aws.yaml
.env.example
```

This avoids hardcoding environment-specific values directly into the code.

### It Includes Orchestration

Airflow DAGs show how the pipeline is scheduled and monitored.

The DAGs separate:

- ingestion
- Bronze to Silver
- Silver to Gold
- data quality scanning

### It Includes Tests

The project includes pytest tests for:

- event generation
- data quality checks
- transformation logic
- Bronze to Silver integration
- Gold aggregation integration

This makes the project feel like an engineering repo, not just a notebook demo.

### It Has Dashboard Consumption

The dashboard shows that the pipeline creates real business value.

A portfolio project is stronger when it ends with something a business user can understand.

Possible validations:

- product IDs must exist in product catalog

## 14. How To Explain This Project In Interviews

Use this explanation:

> I built StreamCommerce Lakehouse 360, a production-style e-commerce data lakehouse. The project simulates six real source systems using Kafka producers, lands raw JSON events into S3-compatible storage, processes data through Bronze, Silver, and Gold Medallion layers, applies reusable data quality checks, quarantines invalid records, and powers a Plotly Dash executive dashboard. It runs locally with Docker and MinIO, and it is designed to map to AWS S3 and Databricks in cloud mode.

Then explain the layers:

> Bronze keeps raw data for audit and replay. Silver cleans, deduplicates, validates, and quarantines bad records. Gold creates business-ready tables for revenue, customers, products, inventory, payments, and data quality.

Then explain robustness:

> The project is robust because it does not assume perfect data. It intentionally generates bad records, validates them, records DQ results, quarantines failures, and keeps the raw layer available for replay.
